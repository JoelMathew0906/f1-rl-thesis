# Thesis-ready SHAP figures/tables — README

The `figures/` and `tables/` subdirectories are generated by
[`scripts/build_thesis_shap_figures.py`](../../scripts/build_thesis_shap_figures.py),
which is read-only with respect to the environment, training and evaluation
code: it does not import `f1_env`, construct an environment, retrain a
model, or re-run evaluation. It only reads existing CSVs under
`outputs/experiments/eval/final-v1/`, `data/shap/` and `output/`, and writes
new files under `output/thesis-shap-figures/figures/` and
`output/thesis-shap-figures/tables/`.

**This README.md file is hand-maintained documentation and is NOT written
by the script.** The `s_0`..`s_17` feature-name mapping used throughout is
also hard-coded in the script (`FEATURE_NAMES`), not read from any doc at
runtime — see §2. Regenerate the figures and tables with:

```bash
PYTHONPATH=src .venv_f1/bin/python scripts/build_thesis_shap_figures.py
```

**After running that command, this README must be reviewed by hand** to
confirm its numbers, table row counts and figure descriptions still match
the regenerated files — the command does not update this file.

## 3. SHAP internal-consistency check (Pass 1.3)

**The requested check — sum of per-feature SHAP values equals the model
output's difference from its base/expected value, within float tolerance —
cannot be performed on these artefacts, and this is stated rather than
skipped silently.** Reading `src/f1_rl_safety/shap_surrogates.py`
(`train_surrogate_and_shap`): `shap.KernelExplainer.shap_values(...)`
returns a full signed per-sample matrix and has a `.expected_value` (the
base value), but the code immediately reduces it —

```python
shap_values = explainer.shap_values(X[:n_eval])
mean_abs_shap = np.mean(np.abs(shap_values), axis=0).reshape(-1)
```

— and only writes `mean_abs_shap` to `data/shap/*.csv`. The signed values,
the base value and the surrogate's raw predictions are never persisted
anywhere in the repository. There is nothing on disk to check additivity
against, for any of the 45 files.

**Substitute check that the persisted data does support:** is "zero
importance" itself stable, i.e. do the same features register exactly 0.0
in every single run rather than just most? Checked across all 45 files
(`output/shap_overall_feature_ranking.csv`, `max` column): **`gap_ahead`
(s_3), `gap_behind` (s_4), `tyre_compound_3` (s_14), `tyre_compound_4`
(s_15) and `track_status_1` (s_9) are exactly 0.0 in all 45 of 45 runs.**
That is internally consistent (not a mix of zero and near-zero noise), and
is plausibly explained by those state dimensions being constant or
near-constant across the rollout samples each surrogate was fit on (e.g. a
single-car race has no varying `gap_ahead`/`gap_behind`) — offered as a
plausible reading of the pattern, not a verified cause. All 45 files also
pass basic schema checks: exactly 18 features each, all values >= 0 (they
are already absolute values).

**A methodological caveat that follows from the same code and matters for
every figure below:** SHAP here explains a small **linear surrogate**
(`torch.nn.Linear`, 200 epochs) trained to imitate each trained policy's
chosen action (continuous risk level for PPO/A2C/REINFORCE, discrete action
index for DQN/SARSA) from the state — **not the policy network itself, and
not reward or crash outcome.** It is a second-order approximation of "what
did this policy's action look like as a function of state, on ~100
rollout timesteps." Treat every SHAP figure below as evidence about the
surrogate's fit to the policy's behaviour, not a first-order explanation of
the RL agent's value function. Also, because each algorithm's surrogate is
fit independently, **raw SHAP magnitudes are not comparable across
algorithms** — e.g. REINFORCE's largest per-architecture mean |SHAP| value is
0.045 (`tyre_wear`) versus DQN's largest at 0.341 (`fuel_norm`), roughly 7.6x
smaller, per `output/shap_per_architecture_ranking.csv`; only within-algorithm,
across-regime comparisons are treated as informative here.

## 4. Seed-consistency analysis (Pass 2)

`tables/table_seed_level_metrics.csv` gives, for every (algo, regime, seed):
`finish_rate`, `crash_rate`, `catastrophic_rate`, `mean_completed_laps`,
`mean_lap_fraction`, `mean_risk`, `mean_pit_stops` — each the mean over
that seed's 100 evaluation episodes. `crash_rate` = `terminated_by_crash`
mean; verified 0 mismatches against the `crashes` column across all 4,500
rows. `finish_rate` = 1 − `crash_rate`. `tables/table_regime_aggregate_metrics.csv`
adds the mean/std/min/max across the 3 seeds per (algo, regime).

`tables/table_seed_consistency.csv` computes, for every algorithm x the 3
regime pairs (`safe − unconstrained`, `rulebook − unconstrained`,
`safe − rulebook`) x 3 metrics (`crash_rate`, `finish_rate`, `mean_risk`) =
**45 (algo, comparison, metric) triples**, the per-seed signed delta and
whether all 3 seeds agree in sign.

**Result: 25/45 (55.6%) are sign-consistent across all 3 seeds; 20/45
(44.4%) are not.** The task brief's stated prior figure was "56% of
comparisons show seed disagreement." This script's own recomputation, on
its own specific choice of 3 metrics x 3 regime pairs x 5 algos, finds
44.4% disagreement — the same order of magnitude and roughly consistent
with that figure, but not numerically identical, because the prior audit's
exact comparison set is not present in this repo to reproduce exactly (see
§0: no `seed_consistency.csv` exists to check against directly). Both
numbers point the same way: **more than 4 in 10 of these regime
comparisons flip sign depending on which training seed you look at.** That
is the basis for treating only a small, checked subset as citable.

Rows 1, 2 and 4 are the "3–5 primary comparisons" requested. Row 3 is
supporting detail. Row 5 is the required deliberate instability example.
Row 6 answers the straights-vs-corners question honestly: it reports
descriptive three-seed means for DQN (corners) and PPO (straights) while
explicitly stating that both rankings reverse in one of the three seeds —
the same kind of outlier-seed sensitivity that row 5 illustrates, just
partial rather than total.

**SARSA is not the subject of any primary claim.** Its crash-rate seed
deltas flip sign in all 3 of its regime-pair comparisons
(`table_seed_consistency.csv`), and its within-cell `mean_risk` values swing
between −1.0 and +0.50 across seeds even within one regime — it is the
least seed-stable algorithm in this grid overall and is used here only as
a comparison point in Figure 6, not as a standalone claim.

## 8. What this directory does **not** claim

- It does not claim any regime "causes" a crash-rate or risk change — n = 3
  training seeds per cell supports an *observed, direction-consistent
  pattern* at most, never a tested causal effect.
- It does not present SHAP importance as an explanation of the RL policy or
  its reward — it explains a small linear surrogate fit to the policy's
  chosen action (§3).
- It does not rename any SHAP feature to a segment/region/corner name —
  no SHAP feature is a segment identifier (§2).
- It does not use REINFORCE-safe's pooled numbers as evidence of anything
  other than seed instability itself.
- It does not modify, retrain, or re-evaluate anything upstream of the CSVs
  it reads.
